# ADR-0006：Broker 離線時由 Gateway 保存量測並補送

日期：2026-10-24。狀態：核心方向已決議；細節待討論，尚未實作與驗證。

## 情境與目標

Broker 暫時離線或 Gateway 無法確認發布成功時，Gateway 仍持續採集。量測保存在 Gateway 本地持久儲存，連線恢復後補送，接受資料入庫延遲。

## 決策

- 成功採集並建立訊息後，先寫入本地待送佇列，再嘗試發布 MQTT，避免發布失敗後尚未保存就退出的空窗。
- 收到成功 PUBACK 後，才將該筆移出待送佇列；連線失敗、逾時或斷線而未取得成功確認時，保留供後續補送。
- 補送沿用原 topic、payload、message_id 與 acquired_at，不把歷史量測重新標成當下取得的新訊息。
- 未收到 PUBACK 不等於 Broker 沒收到；接受重複投遞，搭配 Receiver／DB 既有去重機制。
- 待送資料需能在 Gateway 程序重新啟動後恢復；儲存方式及其持久化保證實作前另定。

## 容量淘汰的紀錄要求

- 若容量策略需要淘汰待送資料，每次淘汰記錄一筆 log，包含原因與本次實際丟棄筆數，讓歷史缺口可追查。
- 此階段不為此新增資料表、監控平台或累計統計功能。
- 淘汰策略依業務情境決定；本 Demo 已同意預設淘汰最舊待送資料並記錄筆數，不預先建立可插拔策略框架；容量數值仍待實作時明列。
- 被容量策略淘汰的訊息不再屬於可補送的資料；保留保證須明確包含此限制。

## 責任與邊界

- Gateway 負責保存尚未確認送達 Broker 的量測，以及恢復後補送。
- PUBACK 代表 MQTT 發布確認，不代表 Receiver 已入庫，也不直接保證 Broker 已同步寫入磁碟。收到成功 PUBACK 後的 Broker 資料保護另行討論。
- 本決策不保證 Gateway 主機／磁碟損壞後仍能恢復本地資料；已採集但尚未成功本地保存的量測，也不在保留保證內。
- 容量與磁碟正常的前提下繼續採集；不宣稱可無限保存。容量耗盡時的採集與資料處置尚未定案。
- Receiver 故障恢復仍依 [ADR-0005](0005-receiver-recovery.md)，不另加 Receiver 本地訊息儲存。

## 待討論

- 已同意採 Python 內建 SQLite，不新增套件；交易與故障恢復方式待實作。
- 保留容量與時間、磁碟滿或寫入失敗時的處理。
- 重連間隔、補送順序與速率，以及積壓補送如何與持續採集並行。
- Broker 自身持久化、重啟與主機故障的保障範圍。

## 預定驗收

1. Broker 停止期間，Gateway 仍產生並保存新量測；恢復後可補送。
2. 有待送資料時重新啟動 Gateway，仍能恢復待送內容與原始訊息身分。
3. 模擬確認遺失／重送，既有去重機制不產生重複量測。
4. 容量上限、磁碟故障及補送排程的案例，在對應策略定案後補齊。

## 目前實作

尚未實作本地待送佇列。現有 Gateway 持續模式只記錄單輪發布失敗，之後重新採集，不保留或補送失敗訊息。
