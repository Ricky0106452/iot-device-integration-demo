# ADR-0006：Broker 離線時由 Gateway 保存量測並補送

日期：2026-10-24。狀態：Gateway 持續模式已實作，完成本地交易與獨立環境的故障補送驗證。

## 情境與目標

Broker 暫時離線或 Gateway 無法確認發布成功時，Gateway 仍持續採集。量測保存在 Gateway 本地持久儲存，連線恢復後補送，接受資料入庫延遲。

## 決策

- 成功採集並建立訊息後，先寫入本地待送佇列，再嘗試發布 MQTT，避免發布失敗後尚未保存就退出的空窗。
- 收到成功 PUBACK 後，才將該筆移出待送佇列；連線失敗、逾時或斷線而未取得成功確認時，保留供後續補送。
- 補送沿用原 topic、payload、message_id 與 acquired_at，不把歷史量測重新標成當下取得的新訊息。
- 未收到 PUBACK 不等於 Broker 沒收到；接受重複投遞，搭配 Receiver／DB 既有去重機制。
- 待送資料需能在 Gateway 程序重新啟動後恢復；儲存方式及其持久化保證實作前另定。

## 容量淘汰的紀錄要求

- 若容量策略需要淘汰待送資料，每次淘汰記錄一筆 log，包含原因與本次實際丟棄筆數，讓歷史缺口可追查。
- 此階段不為此新增資料表、監控平台或累計統計功能。
- 淘汰策略依業務情境決定；本 Demo 已同意預設淘汰最舊待送資料並記錄筆數，不預先建立可插拔策略框架；預設容量 10000 筆，可由啟動參數調整。
- 被容量策略淘汰的訊息不再屬於可補送的資料；保留保證須明確包含此限制。

## 責任與邊界

- Gateway 負責保存尚未確認送達 Broker 的量測，以及恢復後補送。
- PUBACK 代表 MQTT 發布確認，不代表 Receiver 已入庫，也不直接保證 Broker 已同步寫入磁碟。收到成功 PUBACK 後的 Broker 資料保護另行討論。
- 本決策不保證 Gateway 主機／磁碟損壞後仍能恢復本地資料；已採集但尚未成功本地保存的量測，也不在保留保證內。
- 筆數滿時淘汰最舊待送記錄並記 log；實體磁碟滿、檔案無法寫入或 SQLite 操作失敗時，記 outbox_storage_failed 並以非零結束，不繼續假裝資料已保存。
- Receiver 故障恢復仍依 [ADR-0005](0005-receiver-recovery.md)，不另加 Receiver 本地訊息儲存。

## 實作選擇

- 使用 Python 內建 sqlite3，不增加套件；預設檔案 data/<gateway-id>-outbox.sqlite3，可用 --outbox 指定。本地執行資料由 Git 忽略。
- 使用 synchronous=FULL；以序號保存 topic 與原 JSON payload。每次新增前在同一交易計算容量、淘汰、寫入；新增失敗整筆回滾。禁止 :memory:，保存成功才記 telemetry_buffered。
- --max-pending 預設 10000 筆，以新增時的總筆數檢查；調小上限於下次新增時淘汰超量記錄。不額外設定時間過期；這是筆數上限，不是 SQLite 檔案大小上限。刪除後檔案空間可重用，不保證立即縮小檔案。
- 主執行緒依 --interval 採集與保存；單一發布執行緒 FIFO 補送，不在通訊期間持有 SQLite 鎖。--retry-interval 預設 5 秒，失敗後等待再試；成功後立即處理下一筆，不為每筆額外等待採集間隔。
- 每次補送沿用既有發布函式，建立／關閉 MQTT 連線，仍有 --mqtt-timeout。恢復速度受網路、Broker 與單筆連線成本限制，不承諾任意吞吐量。
- 發布執行緒非預期失敗會傳回主執行緒，停止程序，不默默停止補送而繼續堆資料。Ctrl+C 停止採集並等待當次發布結束，剩餘資料留在 SQLite，不強制排空。
- 一份 outbox 只由一個 Gateway 程序使用，且重啟沿用同一檔案；同時啟動另一個實例需另用檔案。本階段不實作跨程序／跨主機接手或分散式鎖。
- --max-pending 到達上限仍可能淘汰正在發布的舊記錄；無法撤回已送出的封包。outbox_discarded 的 dropped_count 是實際移除的未確認記錄數，不等於已證實從未到達 Broker 的訊息數。
- 單次 gateway.publish_once 保持直接發布診斷行為，不使用 outbox。

## 另行設計的議題

- Broker 自身持久化的落盤／故障保障與整體容量策略。
- Gateway 主機／磁碟損毀的資料恢復、跨主機接手與多實例協調。

## 驗收結果

1. 已驗證：Broker 停止期間，Gateway 仍產生並保存新量測；恢復後可補送。
2. 已驗證：有待送資料時強制終止並重新啟動 Gateway，仍能恢復待送內容與原始訊息身分。
3. 已驗證：實際發布後注入呼叫端未取得確認，保留並重送相同資料，既有去重機制不產生重複量測。此為確認不確定的故障注入，不宣稱實際攔截網路 PUBACK。
4. 已驗證：容量淘汰計數、插入失敗回滾淘汰、刪除失敗保留、無法開啟儲存位置，以及網路等待不阻塞本地保存。磁碟寫入故障採 SQLite 錯誤注入驗證，未進行實體斷電或磁碟破壞測試。

## 驗證與操作

完整回歸為 126 個測試通過；獨立完整流程另驗證六筆離線資料經 Gateway 強制終止、重新啟動及 Broker 恢復後補送，最終為十三份快照、五十二筆點位值，確認重送不重複入庫。測試資源均已清理，未更動展示 Broker／資料庫。

操作、容量限制與重現步驟見 [Gateway 離線補送驗證](../verification/gateway-offline-buffer.md)。
